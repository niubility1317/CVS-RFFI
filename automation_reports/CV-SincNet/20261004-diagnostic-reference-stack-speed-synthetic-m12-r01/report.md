# R2耗时分析与后续执行加速

本次为源日志分析和合成输入执行诊断，不访问目标评分，不使用正式checkpoint。正式136行实验的训练预算、科学配置与测试矩阵保持原登记。

## R2为什么慢

- R1每轮50次、200轮共10000次更新；R2为匹配半监督U迭代预算，每轮222次、共44400次，是4.44倍。R2即使关闭伪标签也继续相同步数，不能把两个阶段的“200轮”当作同等训练量。
- R2恢复原生双分支及损失执行框架，reference识别骨干之外仍保留干扰分支。参数数量变化不等于等比例耗时变化。
- 当前16行完整日志扫描包含597929条完整step记录；没有发现stdout中的Traceback、OOM、非有限故障或异常重启。日志均处于写入中，未闭合gzip尾部已单独说明，没有把尾部当数据损坏。
- 第91至130轮大部分行每轮约74至77秒；伪标签行第131轮后增加到约98至102秒，约增加30%。EMA-only行未出现同样幅度，说明伪标签教师/无标签路径是额外成本。时段和GPU共享存在混杂，不将该观察当作精确算子归因。
- 原生每轮完整验证27000个源V样本，并为源域几何诊断再次前向；200轮单次遍历已有540万样本，第二次重复特征计算可以复用。
- 旧实现逐参数梯度检查/多次范数计算、逐标量GPU回传，以及每轮重写全部历史日志增加执行开销。R2没有完整子阶段计时，不能从日志臆测各项百分比。
- 每GPU两训练进程提高并发吞吐，但单进程共享计算资源；现有记录不是单卡一行/两行严格配对试验，不编造提速倍数。

## 本次采用的执行优化

1. 仅开启a1_gradient_snapshot，保留逐参数float32范数和Python累加顺序；裁剪后重新采样，不复用过期梯度。
2. 同轮源V特征复用：128MiB上限、同模型版本/相同输入才命中；输入/参数变化回退原前向，第二个loader仍完整消费。
3. 日志标量按device/dtype批量回传，保留每步全部数据、非有限值null规则。
4. 原生完整epoch日志增量落盘，CSV字段扩展时重写；compact JSONL/CSV仍保留完整历史。新增execution_epoch.jsonl记录验证耗时与缓存命中，便于核实实际收益。

不改200轮、222次更新、batch、优化器、损失、增强、教师更新、FP32/TF32、选模、数据或物理ID。a1_runtime_fast保持False。R2不停止、不重启、不热改；新独立执行release只路由尚未启动的R3–R6。每卡最多两实验、全136行冻结后预测、clean和六个完整residual场景及truth-last评分链均保持。

## 验证及速度证据

原FP32 CUDA未开启确定性算法，原始对原始的重复运行也存在小数值差异。因此不能将不同进程位级差异直接认定为加速错误，也不能仅比较初次CUDA预热总耗时。R2/R3/R4额外用确定性CUDA执行；DAOT中的CUDA median不支持该确定性模式，保留失败诊断，在CPU确定性路径检验R5/R6完整状态。正式任务不启用诊断中的确定性开关。

## 已完成诊断

六组严格一致性与六组本地GPU短窗口计时已完成，诊断状态ANALYZED。CUDA profiler仅作为瓶颈证据：R6完整组合两步窗口记录130069次kernel launch、9406次stream synchronize、1258次quantile，包含约1.034秒CPU信道模拟；profiling有额外开销，未据此推算正式运行耗时比例。当前优化没有消除全部小算子开销，R5/R6的端到端收益较小，不能宣称数倍加速。
